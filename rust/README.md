# Rust port (issue #47, SPEC.md milestone M6)

A partial Rust port of `zel`. Step 1 (issue #47) was a spike to decide whether a full port was worth it; the decision was a phased port, recorded as milestone M6 in `SPEC.md`. It is not installed anywhere yet. The Python CLI stays the product and the reference until cutover (R5).

## What is ported

| Command                                                                           | Python source                                                                                                                                  |
|-----------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| `zel backup [--json]`                                                             | `backup.py` (writer), `cli.backup` – the JSONL file is byte-identical to Python's                                                              |
| `zel validate <changeset> [--json]`                                               | `write/contracts.py`, `write/expand.py`, `taxonomy.py`, `cli_change.validate`, `apply.summarize` – the plan file is byte-identical to Python's |
| `zel status [--json]`                                                             | `cli.status`, `status.py`, read half of `backup.py` and `write/changelog.py`                                                                   |
| `zel audit tags\|collections [--since N] [--json]`                                | `audit/runner.py`, `report.py`, `tagmess.py`, `hygiene.py`; loads `taxonomy.yaml` first, as Python does                                        |
| API reads (items, collections, tags, settings, library version, item-type schema) | `client.py`: pagination and probe, Backoff/Retry-After, 429/503 retries, key redaction, per-session schema cache                               |
| Credentials, data dir, `config.yaml`, `taxonomy.yaml`                             | `config.py`, `taxonomy.py` (load and lint), both read through `src/pyyaml.rs` as PyYAML reads them                                             |

Other audit checks, the registry check among them, and every other command are not ported. `zel audit` with no check, or with an unported one, exits 2 and says so.

## How it is checked

`tests/test_rust_differential.py` runs both CLIs against one `FakeZotero` and identical data directories. Both run with the clock frozen at one instant (Python in-process, Rust through the debug-only `ZELADOR_NOW`), so timestamps and ids compare exactly. It covers 11 commands × 9 scenarios: normal, a forced pagination probe, a 429 retry, a 403 whose body leaks the key, a Backoff header, a 302 that must not be followed (run for `status` only), a library unchanged since the last backup, number text Python would not write (`0.00001`, `1E5`, `-0`; `backup` only), and a seeded `config.yaml` plus registry. Five more cases pin the default config and data dirs to platformdirs' XDG rule. `zel validate` has 203 cases of its own, in `tests/test_rust_differential_validate.py` (the shared bridge, runners and fixtures live in `tests/rust_harness.py`), each a changeset file in the data dir's `changesets/` against a fake library and registry built for it: every op alone, composed on one item and on one collection, ops on objects created earlier in the same plan, no-op writes (same creators with reordered keys, a merge into a tag the item already holds, empty stale fields `set_item_type` must leave alone), a key the API lists twice at two versions (merge_tag pins the entry it walks), a cycle that exists only after an earlier move, both risk tiers, `create_item` with and without an adopted attachment, settings drift (colours differ, order differs, setting unset, only key order differs, no registry), every semantic failure (unknown key, alias, non-canonical tag, `extra`, invalid field, creator type or item type, exclusivity, missing collection, cycle, unadoptable attachment), a schema lookup the server refuses (exit 1), every structural lint error with Python's `repr` of the offending value, 17 kinds of text that is not JSON with CPython's message and position, a changeset nested exactly 1000 levels deep, a 429 retry, no backup, and 36 defective or edge-case registries, each run through both `validate` and `audit tags` – among them YAML 1.1 scalars (`coloured: no`, `On`/`Off`, quoted `'no'`, `010`, `0_0`, `1:30`, `.inf`) and merge keys, plus `exclusive: no` and boolean aliases driven through a changeset. Two Rust-only cases pin that nesting past 1000 levels (up to 300,000 `[`) is refused with exit 2, never a crash. Twenty fail-closed cases pin YAML the port cannot read as PyYAML does – explicit tags, tabs, number spellings only YAML 1.2 reads as numbers, a timestamp folded over two lines: each records Python's exit code and asserts that Rust refuses with exit 1, naming the file and the reason, before any request. The golden changeset in `tests/golden/` validates to `tests/golden/plan.json` byte for byte. Client-generated keys come from `ZELADOR_KEYGEN_PREFIX` in Rust, a debug-only seam like the others, and from a patched `_generate_key` in Python, both yielding `NEWC0001`, `NEWC0002`, …

It asserts equal exit codes, stdout, stderr, files written and API request sequences. The Rust binary reaches the fake through a localhost bridge, using `ZELADOR_API_BASE`, a Rust-only test seam that only debug builds honour.

The suite catches every one of these planted bugs: lowercase instead of casefold, a removed pagination probe, compact JSON separators, no key redaction; and for `validate`: an overwrite marked low-risk, `add_tag` walking its keys backwards, `repr` always choosing single quotes, alias detection skipped, JSON error positions counted in bytes, a slug check without Python's `$`-before-newline, exclusivity that ignores a stock violation, a merge that re-adds a target the item holds, a collection working copy that is not kept, a `set_creators` no-op emitted, `set_item_type` clearing empty fields, and a cycle check that ignores earlier moves.

```bash
uv run pytest -q tests/test_rust_differential.py tests/test_rust_differential_validate.py   # builds rust/ with cargo first; skips without cargo
cd rust && cargo test --locked && cargo clippy --locked -- -D warnings
```

Against a real library of several thousand items, `status --json` and `audit collections` matched byte for byte apart from timestamps. The one difference was the repo-root finding below.

## Findings for the go/no-go decision

1. **Compatible output is a layer of its own.** Agents read `--json` byte for byte, and Rust's defaults differ from Python's: `serde_json` writes `{"a":1}`, Python writes `{"a": 1}`. Numbers too: serde_json keeps each number's source text (`arbitrary_precision`), and `py_number` re-renders it as Python would after `json.loads` – integers with every digit, `-0` as `0`, floats by `repr` (`1e-05`, `1e+16`, `100000.0`). `src/pyjson.rs` reproduces `json.dumps` (compact and `indent=2`), `repr()`, f-string `str()` and `:g`. `casefold()` comes from `caseless`, `isprintable()` from `unicode-general-category`, and `isoformat()` drops a zero fraction. Every further module will hit more of these. Changing the output contract once, deliberately, would be cheaper than mimicking it forever.
2. **Config location must be decided first** (resolved in M6 R1: both implementations now read the platform config dir, and the differential test seeds it). Python found `.env`, `config.yaml` and `taxonomy.yaml` next to its source. The binary used the checkout it was built from, which a distributed binary would not have. The live run showed this: the binary built in a worktree reported `taxonomy_yaml: false` while Python reported `true`. A full port needs a platform config dir, and Python should move to it too.
3. **The library mapping in #47 is partly stale.** `serde_yaml` is deprecated on crates.io, so this uses `serde_yaml_ng`. `reqwest` 0.13 puts `RequestBuilder::query` behind a `query` feature, and its default TLS is now rustls, with no system OpenSSL.
4. **No speed case.** On a real library, `audit collections` spent well under 1% of its wall time on Python CPU; the cost is Zotero rendering bibliographies. A faster Rust run that came second probably hit a warm server cache, so it is not a fair comparison.
5. **Known unpinned differences.** Most need malformed input or a broken setup; the YAML refusals, the nesting limit and the key source can also arise from well-formed input. Where the port cannot be sure it reads input as Python does, it refuses: a difference may turn a Python plan into a Rust refusal, never the reverse.
   - Change-loop input Python crashes on with a traceback. Rust reports a clean error for an op that is not a string (`"op": ["trash_item"]`, exit 2), `taxonomy.yaml` that is not valid YAML, a colour that is not a string, `aliases` that is a number, and a changeset that is not UTF-8 (exit 1). It carries on for a `move_collection` whose parent chain reaches a collection missing from the library (the walk ends there) and an item touched by a write that has no `tags` array (read as empty).
   - Nesting: a changeset nested deeper than 1000 levels is refused with exit 2. CPython has no fixed limit; it accepts nesting until its C stack runs out (about 65,000 arrays on Linux) and then crashes with RecursionError.
   - JSON that CPython reads and serde_json refuses: `NaN`, `Infinity` and lone surrogate escapes in a changeset make Rust exit 2 with serde_json's message, while Python goes on to lint the value.
   - Client-generated keys come from std's `RandomState` (OS-seeded SipHash) in Rust and from `secrets` in Python; keys need to be unique, not secret.
   - Malformed input: an HTTP-date `Retry-After`, a non-numeric `Backoff`, a response without `Last-Modified-Version`, log entries with missing or non-string fields, a non-UTF-8 file in `log/`, `meta.type` of `1.0` or `true`, lone JSON surrogates. Python raises or crashes; Rust tolerates the input or prints a clean error.
   - Config parsing: a malformed `.env` line stops dotenvy, so later variables never load, while python-dotenv warns and continues.
   - YAML (`config.yaml`, `taxonomy.yaml`): `src/pyyaml.rs` re-resolves plain scalars by PyYAML's YAML 1.1 rules and applies merge keys and duplicate keys as PyYAML does. What it cannot be sure of it refuses with exit 1, naming the file: any tab character, even inside a quoted or block scalar (PyYAML refuses most tabs); any explicit tag (`!!str no`, `!<…>`, `%TAG`), because serde_yaml_ng resolves tags before the loader sees them; any plain word YAML 1.2 reads as a number and PyYAML as text (`0o0`, `0e0`, `-.0`, `1e3`, `+.5`), because it arrives with its text gone and would flip a flag or rename a family; and any word PyYAML reads as a date, including one folded over two lines, and `.nan`. The guard scans words outside quoted scalars, comments and block scalars, so it also refuses a `!` or such a word inside a multi-word plain scalar (`description: wow !`), where Python would accept the file. A file starting with a UTF-8 byte-order mark is refused (serde_yaml_ng reports more than one document) where PyYAML reads it. An integer past 2^128 arrives as a float, and YAML syntax-error wording is not matched.
   - JSON: an integer longer than 4300 digits is refused by Python's `json.loads` and written by Rust; a number that overflows a float (`1e400`) is written as `Infinity` by both, which Python's reader accepts and serde_json's refuses, so Rust cannot read back such a backup; a lone surrogate (`"\ud800"`) fails Rust's parse at the API response and Python's write later.
   - Formatting and platform: `fmt_g` matches Python's `:g` only for whole numbers and short fractions; transport-error wording differs (httpx vs reqwest); Unicode table versions differ for rare characters; on Windows, Python writes the locale encoding with `\r\n` and Rust UTF-8 with `\n`; Windows config-dir and data-dir parity is coded to platformdirs' rule but untested; non-UTF-8 XDG values, an empty `HOME`, ASCII separator characters (`\x1c`–`\x1f`) around XDG values, and a leading `//` resolve differently from platformdirs and pathlib; on Linux the default-dir rule (XDG values stripped, relative ones accepted) is pinned by the differential test.
